# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

An idle/clicker game for an ESP32 with a 240x320 ILI9341 SPI display, five push buttons and a passive buzzer. PlatformIO + Arduino framework, C++. Two halves feed each other: a Cookie-Clicker-style gold economy (mining, buildings, upgrades, gold veins) and an idle combat loop (zones, enemies, item drops, equipment, amulet spells).

## Code style

**Comment sparingly.** Write a comment only when the code cannot say it: a non-obvious constraint, a hardware quirk, a balance number's source, or why something that looks wrong is deliberate. Do not narrate what the next line does, restate a name, label sections, or explain a change in a comment (that goes in the commit). Most functions and members need none. When editing a file, do not add comments to match the existing density; remove redundant ones you touch.

## Commands

`pio` is not on `PATH`; it lives at `~/.platformio/penv/bin/pio`.

```bash
pio run                       # Build
pio run -t upload -t monitor  # Flash and open the serial monitor (115200)
tools/sim/run.sh [--days 3] [--seed 1] [--session 5] [--cps 3] [--log]
```

There are no tests. The **balance simulator** compiles the real `src/game/` for the PC (against `tools/sim/stub/Arduino.h`) and plays a scripted player (active 30 min, then a 5-minute check-in every waking hour, asleep 00:00-08:00), printing each building's first purchase and each zone's unlock and self-farming point. **Rerun it after touching any table** in `GameConfig.h`, `ItemConfig.h` or `CombatConfig.h`; the timing numbers in their comments come from it. For a pure refactor, diffing its output against the previous commit with the same `--seed` proves behaviour did not change.

## Hardware

- **All TFT_eSPI setup lives in `platformio.ini` `build_flags`**, not a `User_Setup.h`, so it survives `pio run -t clean` and library updates. Only the GLCD font (font 1) is loaded; enabling another costs flash.
- **Pins are `const int` at the top of `src/main.cpp`.** Buttons are `INPUT_PULLUP`, so avoid flash pins (6-11), input-only pins and strapping pins (0, 2, 5, 12, 15).
- **D-pad:** right (23) next screen, left (26) previous screen / back, confirm (27, red cap), up (19), down (22).
- **`hardware/` holds the carrier PCB, generated by `generate_pcb.py`** (KiCad 10 `pcbnew` + Freerouting; `build.sh` adds DRC and Gerbers). Its `ESP_NETS`/`DISPLAY_NETS` mirror the pins, so a pin change must be repeated there. Edit the script, never the `.kicad_pcb`.

## Architecture

### Main loop
`src/main.cpp` owns every object as a global and wires them in `setup()`. **No blocking `delay()` in game code**: every periodic component takes `now = millis()` and self-throttles. `GameState::update()` and `CombatState::update()` run every loop whatever screen is visible.

Elapsed time uses unsigned subtraction (`now - last`), deadlines a signed difference (`(long)(now - deadline) >= 0`), so both survive `millis()` rollover. Deadlines are pushed from `now` (`deadline = now + interval`), never accumulated, to avoid catch-up bursts.

**Global declaration order matters:** `Achievements`/`Unlocks`/`Inventory` → `GameState` → `CombatState`, since each holds references to the earlier ones.

### Screens
`ScreenManager` cycles through screens in `addScreen()` order: Mining → Buildings → Upgrade → Awards → Zones → Combat → Inventory. All but Mining start locked; `src/game/Unlocks.h` opens them one at a time and `applyUnlocks()` in `main.cpp` maps features to screens. Zones and Combat must unlock together (entering a zone jumps to the next screen).

Header nav labels are computed from the nearest *unlocked* neighbours. The size-2 title and size-1 labels share a 28px bar, so **nav names stay at 9 chars or less** (hence "Awards").

A `Screen` subclass declares its `UI` elements as **members**, initializes them in the init list, registers them once with `addElement(&member)` and `setHeader(&header)`, then:
- `update(now)` pushes fresh values, gated by `if (!refreshDue(now)) return;` (10 Hz by default, `refreshMs` to change it); input handlers call `forceRefresh()`;
- `onConfirmPress`/`onUpPress`/`onDownPress` handle input; `onBackPress` returns **true to consume** Left;
- `onEnter(tft)` resets screen-local state, then calls `Screen::onEnter(tft)`.

Only the visible screen updates, so screens that react to background events diff a monotonic engine counter (`getKillEvents()`, `getDropEvents()`, `Inventory::getRevision()`...) against their last-seen value, and resync it in `onEnter` so they do not replay a backlog.

A big screen can group elements into a plain class with `addTo(Screen &)`/`setVisible`/`refresh` (`src/screens/combat/EnemyPanel`, `ActionPanel`). `addTo` order still decides render order.

**Modals:** `ScreenManager::openModal(screen)` shows a screen outside the rotation (`ResetScreen`) until `closeModal()`. Meanwhile `getCurrentScreen()` returns it, so update, input and notices go to it, and Right/Left navigation is suppressed. Closing re-enters the screen underneath, which repaints it whole.

**Notifications go through the `Header`:** the main loop calls `getCurrentScreen()->applyNotice(...)` with achievements (gold) or screen unlocks (cyan, waits for an achievement notice), and the header paints it over its whole bar.

### Rendering: dirty flags, no full redraws
`src/ui/UI.h` is the core. Nothing is cleared per frame; each element tracks `dirty` and the bounds of its last draw, and `redraw()` erases only when it became hidden, moved or resized.

- **Every mutator is a no-op on an unchanged value** and calls `markDirty()` only on a real change. Writing fields directly leaves stale pixels; marking dirty unconditionally costs a repaint (a whole SPI blit for a sprite).
- `eraseColor` comes from `addElement()`. An element **inside a filled card** is registered with `addElement(&e, Theme::CARD)`.
- Elements painted outside `x/y/w/h` (e.g. `Text`, positioned by datum) override `erase()`.
- **Overlapping elements cannot erase independently, and registration order cannot fix it** for both transitions. Give each element its own space, composite the region into a `TFT_eSprite` (`OreDisplay`), or have the covering element clear only its own area and `resetDrawn()` what was under it (the combat drop banner).
- Elements are never added or removed at runtime. Lists keep a fixed `ListRow rows[N]` and refill them as `ListView` scrolls, hiding leftovers.

### Colours
**Every UI colour comes from `src/ui/Theme.h`.** Local aliases are fine; raw RGB565 literals are not. Exceptions are art: ore palettes in `GameConfig.h` and `0x0000` as the transparent key of RGB565 icons, which every icon on a non-black surface must pass.

### Game state
- **`GameState`** — gold (fixed-point thousandths, `GOLD_SCALE`; `uint64_t` production), buildings, upgrades, mining level, gold veins. Every income path goes through `creditGold()` so lifetime totals cannot drift. Display numbers only through `src/game/Format.h`.
- **`Inventory`** — one byte per item (0 = not owned, else level; duplicates level up) plus the equipped item per slot.
- **`CombatState`** — current zone, HP, cooldowns, kills, drops, spells.
- **`Achievements`** and **`Unlocks`** hold **no references**: they take the other states as `evaluate()` arguments, which avoids a dependency cycle with `GameState`.
- **`Stats.h`** `resolvePlayerStats()` is the single source of the player's attack/defense/HP.

### Combat balance
Damage is `damageThrough(attack, defense)` in `CombatConfig.h`: **`attack - defense` with no floor**. This is load-bearing; a floor would let the auto-attack grind down anything and make gear optional. All damage math (combat, `ZoneScreen`'s reach labels, the simulator) goes through that one function.

Enemy tables are tuned so **a zone's defense sits at 1.2-1.4x the attack the player arrives with**: the auto-attack is blocked, the strike (`STRIKE_MULTIPLIER`) gets through, so a new zone is fought actively and becomes idle-farmable once its own drops are levelled. Arrival stats and zone timing are measured by `tools/sim` and noted in `CombatConfig.h`. `ITEM_MAX_LEVEL` (10, +135%) stays below the next tier's 3x so levelling never skips a zone. Spells (`SPELLS`, one per amulet) deliberately deal no damage, so they never change which zones are reachable. Actions that would do nothing (`strike()`, `castSpell()`) refuse without spending their cooldown.

### Persistence
`src/game/SaveGame.{h,cpp}` writes one raw `SaveBlob` plus a checksum to NVS. Each state exposes a POD `Snapshot`; `applySave()` restores in dependency order (combat last, since it re-enters its zone). No offline progress: the board has no clock across power-off.

`autosave()` writes every 60 s, brought forward to 5 s on a milestone (`milestoneSignature()`), and skips byte-identical blobs. The interval is a flash-wear budget; don't shorten it casually.

**Snapshots stay POD: primitives and indices into the config tables, never a `String` or pointer.** Adding a field means bumping `SAVE_VERSION`; adding a table row is caught by the `layout` fingerprint. A mismatched save is discarded, with no migration.

Reset: hold Up + Down while powering on, or for 3 s in game (`checkResetGesture()`), which opens `ResetScreen`; Yes erases the save and calls `ESP.restart()`.

### Content is table-driven
Adding content is adding a row to a `static constexpr` table (`*_COUNT` derived via `sizeof`):
- **`GameConfig.h`** — `ORE_TIERS`, `BUILDINGS`, `GOLD_UPGRADES`. Upgrade prices use `AT(building, factor)` so retuning buildings carries the shop along. `BUILDING_BOOSTS` generates five doubling upgrades per building. For `UNLOCK_ZONE` upgrades, `bonusPercent` is the **zone index**.
- **`ItemConfig.h`** — `EquipSlot`, `ITEMS`, `ItemId`.
- **`CombatConfig.h`** — pacing constants, `ZONES`, enemies and drop tables (chance in basis points), `SPELLS`. **Enemy `defense` is the difficulty dial.**
- **`AchievementConfig.h`** — `ACHIEVEMENTS`; a new `AchKind` needs a `case` in `Achievements::getProgress` and in `iconFor` (`AchievementScreen.cpp`).

**`BuildingId` and `ItemId` must stay in the same order as their tables**, and so must `UpgradeScreen`'s `CATEGORY_STYLES` with `UpgradeTarget`. Name length limits are in the per-field comments of each table.

### Assets
**Flash is the binding constraint on art** (a 16x16 RGB565 icon is 512 B). `src/assets/Assets.cpp` holds `PROGMEM` arrays, declared in `Assets.h`, byte-swapped RGB565 with black as transparent. Artist PNGs in `src/assets/png/sprites/` go through `tools/convert_sprites.py`, which regenerates `Sprites.{h,cpp}` (never edit by hand): enemies and zone backgrounds as run-length-encoded palettes, items as 16x16 icons. `src/assets/png/icons/` is an uncompiled source library.

## Performance
Avoid `String` concatenation in refresh paths: use `char buf[N]` + `snprintf` + `setText(const char *)`. For fields constant per list item, track which item each row shows and skip rebuilding (`BuildingScreen::rowBuilding[]`).
